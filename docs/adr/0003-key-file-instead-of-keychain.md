# SQLCipher 密钥改存应用数据目录密钥文件（db.key）

Packsmith 的 SQLCipher 加密密钥不再存放在操作系统钥匙串，改为存放在应用数据目录下的密钥文件 `<appdata>/db.key`（0600 权限，仅当前用户可读）。数据库本身仍是整库加密（加密单库的核心设计承袭 ADR-0002，其威胁模型不变：只拷走 db 文件仍读不出凭据）。

## 动机

用户反馈：每次启动访问钥匙串条目都会触发钥匙串弹窗（macOS Keychain 的 ACL 校验），骚扰且令人困惑；Windows Credential Manager 也存在同类访问摩擦。密钥文件方案做到启动零钥匙串访问、零弹窗。

## 决策

启动时的密钥解析顺序：

1. `db.key` 存在 → 直接使用（完全不触碰钥匙串）；
2. `db.key` 不存在且数据库文件已存在（老版本升级用户）→ 从系统钥匙串读旧密钥 → 成功则写入 `db.key`（0600）并**从钥匙串删除旧条目**（删除为尽力而为，失败仅记录日志）→ 用旧密钥打开既有数据库，用户数据无损；
3. 两者都没有（全新安装）→ 生成新随机密钥写入 `db.key`。

关键安全规则：`db.key` 存在但内容损坏/为空 → 报错拒绝启动，**绝不静默重新生成**（重新生成会让既有数据库无法解密，等同丢数据）；钥匙串读取遇到真实错误（访问被拒、钥匙串锁定）同样必须报错向上传播，而不是当作"没有密钥"。

`db.key` 的写入是原子的（临时文件 + rename），unix 上 0600 权限，其他平台尽力而为（Windows 用户目录下的 ACL 本就限制为当前用户）。

`keyring` 依赖**保留**（否决票面"可从 Cargo.toml 移除"一项）：它只服务于迁移路径②。在迁移窗口期移除依赖会让尚未迁移的老用户的既有数据库直接打不开。一旦 `db.key` 存在，运行期任何代码路径都不会再触碰钥匙串；待确认无老版本存量用户后可再移除。

## 取舍

- 得到：零钥匙串弹窗、零钥匙串依赖（迁移窗口后）、密钥随 appdata 目录一起备份/迁移。
- 失去：**拷贝整个 appdata 目录即等于拿到密钥**，db 文件失去"离开本机即不可读"之外的机器绑定。这是用户明确接受的取舍——本地开发工具的威胁模型是"防 db 文件被单独拷走读出凭据"，不是"防本机用户"；只拷走 db 文件本身仍然不可读（加密测试覆盖此点）。

## 状态

ADR-0002 的"加密单库存放全部数据"核心仍然有效；其中"密钥托管于系统钥匙串"的部分由本 ADR 取代。
